The binding of [EGL 1.5](https://registry.khronos.org/EGL/sdk/docs/man/) for the Erlang and Elixir programming language. It comes with a set of OpenGL [bindings](https://github.com/orgs/erlangsters/repositories?type=all&q=opengl-) which are designed to work with it.

- OpenGL: [3.3](https://github.com/erlangsters/opengl-3.3) | [4.1](https://github.com/erlangsters/opengl-4.1) | [4.6](https://github.com/erlangsters/opengl-4.6)
- OpenGL ES: [2.0](https://github.com/erlangsters/opengl-es-2.0) | [3.0](https://github.com/erlangsters/opengl-es-3.0) | [3.1](https://github.com/erlangsters/opengl-es-3.1) | [3.2](https://github.com/erlangsters/opengl-es-3.2)

Unlike the OpenGL bindings, this one is hand-written. The OpenGL bindings are generated by the OpenGL binding [generator](https://github.com/erlangsters/opengl-x.y-generator).

```erlang
Display = egl:get_display(default_display),
{ok, {_, _}} = egl:initialize(Display).
```

EGL 1.5 is the last Khronos EGL version, which is why the repository name carries that suffix. The Erlang mapping is not a tagged release yet.

Linux is the runtime-verified platform. macOS and Windows compile in CI with [ANGLE](https://github.com/google/angle). They are not a first-release runtime claim.

It does not expose `eglGetProcAddress`, pixmap surfaces, `EGLImage`, or `EGLSync`. OpenGL current-context rules still apply; this binding maps them onto BEAM processes. See [thread safety](docs/thread-safety.md).

Written by the Erlangsters [community](https://about.erlangsters.org/) and released under the MIT [license](https://opensource.org/license/mit).

## Getting started

Pick an OpenGL binding and add both dependencies. Native compilation needs a C compiler, CMake, and EGL. On macOS and Windows set `ANGLE_INCLUDE_DIR` and `ANGLE_LIB_DIR`. The GitHub [workflow](.github/workflows/workflow.yml) is the starting point for packages.

A headless pbuffer path:

```erlang
Display = egl:get_display(default_display),
{ok, _} = egl:initialize(Display),
ok = egl:bind_api(opengl_api),
{ok, [Config | _]} = egl:choose_config(Display, [
    {surface_type, [pbuffer_bit]},
    {renderable_type, [opengl_bit]}
]),
{ok, Surface} = egl:create_pbuffer_surface(Display, Config, [{width, 1}, {height, 1}]),
{ok, Context} = egl:create_context(Display, Config, no_context, [
    {context_major_version, 3}
]),
ok = egl:make_current(Display, Surface, Surface, Context).
```

A GLFW window on Wayland must share GLFW's display connection:

```erlang
{ok, wayland} = glfw:platform(),
NativeDisplay = glfw:display_egl_handle(),
Display = egl:get_platform_display(wayland, NativeDisplay, []),
{ok, _} = egl:initialize(Display),
WindowHandle = glfw:window_egl_handle(Window),
{ok, Surface} = egl:create_window_surface(Display, Config, WindowHandle, []).
```

`get_display(default_display)` remains the pbuffer and ANGLE path. It does not compose with GLFW windows on Wayland.

Destroy each context and surface once. `terminate/1` poisons the display and the interned objects that belong to it.

The test suite is the practical example. Headless CI uses `EGL_PLATFORM=surfaceless`.

## Thread safety

OpenGL needs a current context on an OS thread. The BEAM does not expose OS threads. This binding starts one executor thread per EGL context and binds a process with `make_current/4`.

For more information, consult this [document](docs/thread-safety.md).

## API mapping

This is a binding to a C API that has been slightly adapted to feel more natural in Erlang and Elixir.

> Your existing EGL knowledge still applies.

If a function does not look the way you expect, check the [API mapping](docs/api-mapping.md).

## Native window handle

Sibling NIFs wrap a platform window in an `egl_window` resource that `create_window_surface/4` accepts. GLFW does this in `window_egl_handle/1`. Wayland also needs `display_egl_handle/0` for `get_platform_display/3`.

For more information, consult this [document](docs/native-window-handle.md).

## Command executor

The generated OpenGL bindings call `egl_execute_command` so `gl*` runs on the current context's executor. If you are writing a sibling NIF, that C ABI is documented here: [command executor](docs/commands-executor.md).
